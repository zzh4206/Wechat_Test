# REPLY：v0.6 审批双通道与报告修订流 · 模板侧裁定

> 答复日期：2026-10-20 · 评审人：数据负责人
> 结论：**四项裁决全部给出，按《TECH-v0.6》实施；与 v0.5 合并一次 user_version 4→5 迁移窗口，同意。**

## T1 裁决：修订可见性 = 方案 (b)，**不加 report 列**

采纳 `report_revisions` 镜像表（前端修订时间线是明确需求，段落级历史只有表能承载）。
但**否决 (a) 的轻量列**：`report` 表 v0.4 刚重建过，为两个可推导字段再重建一次不值——
「哪些报告被修订过 / 最近修订时间」用视图推导（`MAX(ts)` GROUP BY），零冗余零重建。

表结构（定稿见 TECH §1.1）：沿用 v0.4 media 的成熟模式——**`source_key TEXT UNIQUE` 幂等键**，
插件重放修订事件不产生重复行；`type/target_ref/summary/source` 全部元数据，红线 §7 已确认不含原文。

## T2 裁决：markings = 方案 (b) 镜像表

「所有未完成事项」跨群/跨期聚合是前端的自然需求，烘正文确实做不了。定稿表 `marking`
（TECH §1.2）：kind 三态（done/undone/deleted）CHECK、`source_key` 幂等、`source` 只存通道名。
**账号维度不需要列**——v0.5 方案甲「每账号一库」已由库路径承载账号隔离（与 v0.5 需求文档自洽）。

## T3 确认：Q1 维持

**审批数据不镜像，维持 v0.4 裁定**。事实源与写入方都在每群库，前端只读每群库；跨设备审批视图若真有需求，另行立项走提案流程。

## T4 确认：定稿 × 修订交互

确认：`upsertReport` 冲突时**保留已有 `final`**（draft→final 单向定稿，修订不降级）；
修订**不改变** status，`final` 被修订后仍 `final`。DAO 侧冲突分支同步实现，测试钉死该语义。

  4→5 一次性迁移只含 v0.6 两张新表 + 视图，真实库迁移前备份惯例不变；
