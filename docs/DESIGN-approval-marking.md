## 0. 两个概念的正名

| | 审批（approval） | 标记（marking） |
|---|---|---|
| 回答的问题 | "这条识别是真的吗？"（真实性确认） | "这件事做完了吗？"（完成状态） |
| 作用对象 | 待确认任务/承诺/事件（`pending_confirm` → `active/cancelled`） | 已确认的任务/承诺（完成进度） |
| 触发模式学习 | ✅（`learned_pattern` 登记） | ❌（与识别无关） |
| 改不改日报 | ✅ 改（修订流，见 §2） | ❌ **不改日报** |
| 进周报/月报 | 间接（经修订后的日报） | ✅ **专门展示**（「完成情况」段） |
| 可否独立发生 | — | ✅ **可以**：没有任何审批的资料也能标记 |

标记的状态枚举：**已完成 / 未完成 / 删除**（删除 = 从后续报告中隐去该条，历史文件不动）。

## 1. 报告修正流（用户指定的级联语义）

```
当日 20:30        生成日报 D
之后任意时刻       审批发生（对话框或前端）→ 影响当日条目
                  → 更新日报 D：对应条目重渲染 + 尾部「修订记录」追加一行
                  → 若本周周报 W 已存在 → 同步更新 W 对应段 + 修订注记
                  → 若本月月报 M 已存在 → 同理
周日 20:40        生成周报 W（读取的日报已是修订后的）
之后该周任意日报/周报的审批 → 更新对应日报 + 同步更新 W
月初 08:00        生成月报 M（读取的日报/周报已是修订后的）
之后该月任何审批   → 逐级同步更新 D → W → M
```

原则：**修订是逐级向上的**（日报是事实层，周报/月报是聚合层；聚合层跟随事实层的修订），且每次修订**简明记录改了什么**。

## 2. 修订的展示形态：日报的「流展示」

报告文件（.md）尾部维护一个**修订记录段**，只追加、不重写历史：

```markdown
## 修订记录

- 2026-10-21 09:12 审批：任务「某课程作业」确认为真（来源：前端）→ L2 对应条目状态更新
- 2026-10-21 20:03 标记：任务「某课程作业」→ 已完成（来源：对话框）
- 2026-10-22 10:00 审批：承诺「下周组会汇报」取消 → L2 移除该条，正文相应收缩
```

规则：

1. **正文修订最小化**：只改动受影响条目所在的段落/行，其余内容字节不动（diff 友好）；
2. **修订行 = 一句话**：时间 + 类型（审批/标记）+ 对象 + 动作 + 来源通道；
3. **流展示**：修订段按时间正序追加——读者从修订段即可看出"这份报告生成之后发生过什么"；
4. 发送侧不受影响：修订不重发 filehelper（避免打扰）；修订后的完整版在前端/文件可见。

## 3. 数据结构

### 3.1 标记事件（v0.2 修订：单一查询副本，插件侧不落表）

~~原设计：每群库新增 markings 表（UNIQUE 覆盖式）~~ **已废弃**——数据负责人架构约束 1：
「同一事实两个家」是本周两次口径事故（summary chat_id 分裂、msg_id 命名空间）的共同根因。
裁定：**marking 的唯一查询副本是 knowledge.db**（`marking` 表 + `v_marking_latest` 视图，TECH-v0.6 §1.2），
插件侧**不落任何第二持久真相**。

现行实现：

- `markTarget(chatId, targetRef, status, source)` 构造标记事件（target_ref=`<chatId>:<kind>:<id>` 全局唯一；
  状态映射 completed→done / incomplete→undone / deleted→deleted）→ **直连镜像通道**
  （knowledge.db `marking` 表，source_key 幂等不可变追加）；
- 镜像失败 → 有界内存队列（500，溢出丢最旧）+ error 日志（含完整事件 JSON 供重放）；
  重放源 = `web/actions.jsonl` 动作日志（本身持久）——重启丢失内存队列可接受；
- 独立于审批的性质不变：tasks.status 管确认状态，marking 管完成状态——两棵树；
- `deleted` 标记：报告渲染时跳过该条，库行保留（可逆）；
- **写入只经服务方法** `markTarget`——**绝不直改 SQL**（直改绕过修订流级联，违反单写者精神）；
- 镜像结果 ≠ 同步可见：前端以 knowledge.db 为准并容忍镜像延迟（已列入数据库负责人函 §三.6）。

### 3.2 修订记录（两级）

| 层 | 存储 | 内容 |
|---|---|---|
| 结构化留档 | 每群库新增 `report_revisions` 表：`(chat_id, kind, date_key, ts, type, target_kind, target_ref, summary, source)` | 机器可查（前端"修订时间线"页） |
| 流展示 | 报告 .md 尾部「修订记录」段 | 人读（由 report.ts 渲染时从 revisions 表取该报告的条目生成，文件内只追加） |

### 3.3 周报/月报的「完成情况」段（标记的展示位）

周报/月报生成与重渲染时，新增一个固定段：

```markdown
## 完成情况（标记）

| 事项 | 来源日 | 标记 | 标记时间 |
|---|---|---|---|
| 某课程作业 | 10-21 | ✅ 已完成 | 10-21 20:03 |
| 下周组会汇报 | 10-22 | ⬜ 未完成 | 10-22 11:30 |
```

- 数据源：该周期窗口内所有日报涉及的任务/承诺的 **markings 当前状态**；
- **日报中不出现此段**（标记不改日报——按定义）；周报/月报中固定出现（有标记才渲染，无标记整段省略）。

## 4. 级联更新的实现

### 4.1 触发点（全部在服务方法内，用户永不直改存储）

```
ApprovalActions.taskConfirm / taskSetDeadline / …
  → 识别服务落库（既有）
  → ReportRevisionService.onApproval(chatId, dateKey)   ← 新增，级联入口
MarkActions.markTarget(…)
  → markings 落库
  → ReportRevisionService.onMarking(chatId, dateKey)    ← 同一入口
```

### 4.2 ReportRevisionService（src/report-revision.ts，新增）

```
onEvent(chatId, dateKey)：
  1. 重渲染日报 D(dateKey) 的受影响段（任务/承诺/事件段）——从 store 取最新状态
  2. 追加 D 的修订行（revisions 表 + .md 尾段）
  3. 若该周周报 W 已存在 → 重渲染 W 对应段 + W 修订行
  4. 若本月月报 M 已存在 → 同理
  5. 全程不触碰 LLM（纯模板重渲染——修订是确定性操作，不该再花钱花时间）
```

- **同步执行**（毫秒级模板操作，不进 regen 队列——队列只留给"重新生成"（LLM 参与）的场景，如错号补发、手动重跑）；
- 周报/月报**不存在**时什么都不做（它们生成时自然读到修订后的日报与最新标记）。

### 4.3 与单写者约束的关系

- 一切落库经 group-store 既有方法 + 新增 `markTarget`/revisions 方法（R3 围栏内）；
- 报告 .md 的修订经 store.writeText（落 stateDir，围栏内）；
- knowledge.db 的 report 行**同步刷新**：走既有 `mirrorReport`（upsert 幂等，行不新增）——注意 status 语义：修订不改变 draft/final（定稿是另一件事，前端 P2 的 `report.finalize` 独立处理）。

## 5. 通道与动作白名单增补

| 动作 | 通道 | 调用 |
|---|---|---|
| 任务/承诺/事件审批 | 对话框 + 前端 | ApprovalActions（confirm-loop 文档 §2.1） |
| `task.mark` / `promise.mark`（params: status） | 对话框 + 前端 | MarkActions.markTarget |
| 修订 | 自动（审批/标记的副作用） | ReportRevisionService——**不作为用户动作暴露** |

## 6. 边界与不做

1. 修订**不触发 LLM**（模板重渲染，确定性）；
2. 修订**不重发** filehelper（打扰最小化；完整版在文件与前端）；
3. `deleted` 标记不删库行、不改历史 .md 的历史段（只从当期渲染中隐去 + 修订行记录）；
4. 跨周期边界的条目（周二审批周一的事）按 **dateKey 归属日**修订——不追溯更早的报告；
5. 月报的修订跟随周报同构（月是周的聚合层）。

## 7. 测试

- 修订流：审批 → 日报对应段更新 + 修订行追加（其余内容字节不变断言）；
- 级联：周报存在时，日报审批 → 周报同步更新；周报不存在时 → 无操作；
- 标记：三种状态、独立于审批（未审批资料可标记）、重标记覆盖、deleted 渲染隐去；
- 展示位：周报/月报含「完成情况」段、日报不含；
- 单写者：全程无直改 SQL（mock 断言只经服务方法）；
- 全离线，全量绿 + build 干净。
