# 技术路线调整报告：本地库读取（wx-chatbot 路线）vs iLink Bot（im-connect 路线）

> 配套：[PRD.md](PRD.md) §8、[REPORT-wechat-group.md](REPORT-wechat-group.md)（结论 b：iLink 协议内微信读群无解）、
> 外部输入：《技术报告-mac端微信群聊读取与应答.md》（用户置备，下称"移植报告"）、[sanjiao403/wx-chatbot](https://github.com/sanjiao403/wx-chatbot)
> 日期：2026-10-11 · 性质：重大方向决策，需产品负责人拍板

---

## 1. 决策背景

微信优先战略（PRD §8）遭遇平台墙：官方 iLink Bot 协议双重锁死（bot 无法入群 + 服务端不投递群消息）。
新选项出现：**wx-chatbot 路线——读取本机微信客户端的本地聊天数据库**，用大号登录即可获得全部群聊消息，无需小号。

## 2. 两条路线逐维比较

| 维度 | A. iLink Bot（现状） | B. 本地库读取（新路线） | 优者 |
|---|---|---|---|
| 能否读到目标群消息 | ❌ 平台锁死，等待腾讯 | ✅ 大号在哪个群就读哪个群，含历史 | **B** |
| 账号要求 | 独立小号 + 扫码维护 | 无需小号，大号日常登录即可 | **B** |
| 消息实时性 | 事件推送（若可用） | 轮询/监听库文件，秒级延迟，够用 | A 略优 |
| 发送能力（二期） | 官方通道可发（私聊） | UI 自动化（剪贴板+CGEvent），灰色但可行 | A |
| 稳定性 | 官方 API，稳定 | **微信每次升级可能破坏读取层**（库结构/加密 key 随版本变） | **A** |
| 封号风险 | 无（官方协议） | 被动读本地文件：低（不碰网络协议）；二期 UI 自动化发送：中 | **A** |
| 隐私暴露面 | 仅白名单群消息流经插件 | **本机全部聊天记录对读取层可见**（含私聊、其他群），必须强隔离 | **A** |
| 数据完整性 | 仅登录后的增量 | 含历史消息（冷启动即有上下文） | **B** |
| 上游依赖 | 依赖 im-connect 项目 | 仅依赖微信客户端本体（版本耦合） | 平手（各有各的依赖） |

**结论：在"读微信群"这一核心诉求上，B 是当前唯一可行路线；A 降级为"未来若腾讯放开则零成本切换的备胎"。**

## 3. 红线重定义（必须由产品负责人确认）

原 PRD 红线："任何逆向个人微信、非官方协议、自动化客户端方案一律排除"。
新路线要求把红线**精确化**为三条，而非简单放弃：

1. ✅ **允许**：读取本机、本人账号、本人设备上的微信本地数据库（被动、只读、不碰微信进程、不碰网络协议）——这与用 SQLite 打开自己 App 的数据文件在风险性质上同类，wx-chatbot 与移植报告均属此类；
2. ⛔ **仍然禁止**：任何协议层逆向/伪造（hook 微信网络、模拟客户端握手、多人共用协议库）——这才是封号与法律风险主体；
3. ⚠️ **受限允许（二期再议）**：UI 自动化发送（剪贴板+CGEvent 模拟本人操作）——灰色地带，MVP 阶段不实现；届时必须有前台检测、用户占用检测、dry_run 三重闸门（移植报告 §2.2 已设计）。

## 4. 架构影响：不需要推倒重来（关键论断）

MVP 已完成的五层（WP1–WP4，43 测试全绿）**没有一行代码关心消息从哪来**：

```
旧：im-connect(补丁) ──im-connect/message──▶ bus.ts ─▶ buffer ─▶ distiller ─▶ journal
新：wechat-db-reader(新) ──相同事件/接口──▶ bus.ts ─▶ buffer ─▶ distiller ─▶ journal
                                                        （persona/journal/guard 原样复用）
```

- 换源只改 `bus.ts` 的上游：新增 `src/source/wechat-db.ts` 适配器，产出现有的 `{chatId, sender, text, messageId, ts}` 结构即可；
- 白名单/令牌桶/注入防护/人格/四类提炼/落盘日报**全部原样复用**；
- 反而变得更纯粹：不再依赖第三方插件 im-connect，**可移除已打的 profile 补丁**（patch -p1 -R 回滚），撤销 B+A 中的 B；
- DSH 插件形态保留：插件运行于宿主进程，天然有读 ~/Library 的权限；读取层需处理磁盘全盘访问授权（macOS TCC）。

**需要重做的部分**（新的关键路径）：
- W1 读取层验证（生死步）：本机当前微信版本（4.x）的库是否可读、加密 key 获取方式、@chatroom 会话表结构——移植报告 §5 步骤 1，先 spike 后投入；
- W2 消息规范化：发送者剥离（`wxid:\n正文`）、系统消息过滤、wxid→昵称映射；
- W3 增量游标：记录每群已读位置，启动时可选择性回灌 N 条历史；
- W4 隐私围栏升级：读取层只暴露白名单群的**增量消息**（不得全库导出、不得读私聊表），数据不落原始消息（与现有 journal 红线一致）；群消息涉及第三人，日报保留期设上限。

## 5. 与 im-connect 框架的关系

| 组件 | 处置 |
|---|---|
| im-connect 依赖 + profile 补丁 | **移除**（回滚补丁、从 profile 卸载），微信路线不再需要；若保留 QQ/钉钉二期可再启用 |
| dsh-group-lurker 插件本体 | 保留，替换消息源适配器 |
| PRD §3「运行前提」 | 改写：大号登录 macOS 微信 + 磁盘/辅助功能授权；不再要求小号 |
| 移植报告的闸门设计（presence/group_gate/guard） | 二期发送功能时吸收 |

## 6. 建议决策与下一步

**建议：采用 B 路线（本地库读取），保留插件架构，移除 im-connect 依赖；红线按 §3 三条精确化。**

下一步（新关键路径，按序）：
1. **W1 spike（生死步，~0.5 天）**：本机微信 4.x 库可读性验证（定位库文件、判断加密、评估 key 获取），产出 REPORT-db-access.md——**失败即全线终止，不硬啃**；
2. W1 通过 → W2/W3/W4 拆分派工，复用现有测试框架；
3. im-connect 卸载与补丁回滚放最后（确认新链路可用后）；
4. 探测实验（REPORT-wechat-group §3c）降为每季度一次的例行检查。

## 7. 风险清单

| 风险 | 等级 | 对策 |
|---|---|---|
| 微信升级破坏读取层 | 高（必然发生） | 适配器接口隔离；失效=静默无数据（只读无副作用），恢复成本=重做 W1 |
| 全库隐私暴露 | 高 | 读取层白名单前置 + 禁读私聊表 + 原始消息零落盘 + 日报保留期上限 |
| macOS TCC 授权流程 | 中 | 文档化一次性授权步骤进 RUNBOOK |
| 群成员知情/冒犯 | 中 | MVP 只读不发言，零打扰；二期发言前另行评估（移植报告 §3.4） |
| key 获取需辅助功能/键链权限 | 中 | W1 spike 首先回答 |
