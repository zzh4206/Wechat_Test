# 事故分析：审批接线缺失导致生产回归（完成任务失效 / 修订流失效 / 来源标错）

- 编号：ANALYSIS-2026-10-20-approval-wiring-regression
- 严重级别：**P0**（生产回归——既有可用行为「完成任务」被新代码破坏，且两项核心承诺静默失效）
- 发现：总负责人实测（2026-10-20 深夜）
- 状态：修复工单已派（在岗 agent 执行中）；本报告为根因分析与流程改进记录

## 1. 现象（用户实测三后果）

| # | 症状 | 影响 |
|---|---|---|
| 1 | 审批后报告不刷新 | 「审批后自动刷新报告」的核心承诺静默失效——修订流看似上线，实际零产出 |
| 2 | 「完成任务」报「完成失败（目标不存在）」 | **生产回归**：改造前此功能正常，语义统一改造后恒失败（对话框+前端双通道皆然） |
| 3 | 前端审批被记成「来源：对话框」 | 审计口径失真，通道统计不可信 |

## 2. 根因链（代码取证）

```typescript
// src/index.ts（主入口）创建 ApprovalActions 时：
new ApprovalActions({ task, promise, notify })        // ← 只传了三个老依赖

// 而 M1/M2 阶段门面新增了三个可选依赖：
constructor(options: {
  task; promise; notify;
  revision?: ReportRevisionService   // ← 可选：不传则 revise() 静默跳过
  marks?: MirrorChannel              // ← 可选：不传则 markTarget 相关恒 false
  source?: 'chat' | 'web'            // ← 实例级默认：两通道共用实例 → 前端被记成 chat
})
```

三个后果的对应关系：

1. **审批不刷新**：`revise()` 调 `this.deps.revision.onApproval`——revision 未注入 → 静默跳过；
2. **完成任务失效（回归）**：`taskComplete` 改为转调 `marks.markTarget('completed')`（完成语义统一改造）——marks 未注入 → 恒返回 false → 「目标不存在」误报。**改造前该功能走状态机直改，是好的——回归由改造引入**；
3. **来源标错**：source 做成实例级默认 'chat'，前端通道没有逐调用覆盖 → 全记 'chat'。

## 3. 为什么四层防线都没拦住

| 防线 | 为什么失守 |
|---|---|
| 开发者自测 | agent 按"新增可选依赖不破坏既有测试"的自检路径走——可选依赖天然不破坏既有测试 |
| 单元/集成测试（440 个） | **测试自己注入 mock 依赖**——依赖注入的便利恰好绕过了主入口：测试图 ≠ 生产图 |
| check-sensitive | 只扫敏感信息，不扫接线 |
| PM 验收 | 复核了测试数量、约束遵从、镜像调用点——**没有从"主入口组装"视角打穿**（与我验收 G1 时的盲区同款） |

**这是同一课第二次发生**：数据负责人在审查里原话——「测试没抓到：新用例直接调 writeReport，没有从生成入口打穿的集成断言」。G1 教训是"测试没从生成入口打穿"，本次是"测试没从**组装入口**打穿"。两次的本质相同：**测试覆盖的是"代码怎么工作"，没覆盖"代码怎么被组装"**。

## 4. 修复方案（工单已派，在岗 agent 执行中）

| # | 修法 | 级别 |
|---|---|---|
| 1 | revision/marks 依赖**可选改必选**——构造签名缺参数 = 编译失败，"静默跳过"这一类 bug 在编译期死掉 | 类别根治 |
| 2 | index.ts 补全接线（revision + marks 镜像闭包） | 直接修复 |
| 3 | source 改**逐调用参数**：ActionInbox 显式 'web'、对话框显式 'chat'——实例级默认废除 | 修复后果 3 |
| 4 | taskComplete 全链恢复验证（两通道 × 完成成功） | 修复后果 2 |
| 5 | **新增 tests/wiring.test.mjs（接线测试）**：按 index.ts 的真实构造方式组装服务图（不 mock 注入依赖），断言 revision/marks 非空、审批真实产生修订行、complete 真实调镜像——**"组装入口打穿"制度化，此类回归从此有哨兵** | 流程改进 |

## 5. 责任与流程改进

1. **PM 验收流程增补**：凡涉及**新增依赖/新增接线**的交付，验收必须包含"主入口组装视角"的核查项（组装参数清单比对），不接受"测试全绿"作为接线正确的证据；
2. **哨兵测试扩展**：wiring.test.mjs 进入哨兵清单（与 no-send 同级——削弱须单独提交说明）；
3. **可选依赖使用规约**（写入 CONTRIBUTING）：服务类的可选依赖仅限"真正的运行时开关"（如 webActionsEnabled）；**协作必需的协作对象一律必选**——缺参应在编译期暴露，不应在运行期静默。

## 6. 与既有缺陷的关系
