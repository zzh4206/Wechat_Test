# 交接简报：sender 自动定位发送（免除"文件传输助手须常驻前台"前提）

> 致：负责解决"不依赖打开/全屏/点击对话框也能发消息"的专人
> 交接人：PM
> 日期：2026-10-16
> 预算参考：调研与探针资产已就绪（见下），核心方案已验证可行，预估 1–1.5 天

---

## 1. 你要解决的问题（一句话）

当前 sender 的发送原语是"激活微信 → 剪贴板粘贴 → 回车"，它会打进**当前打开的会话**——因此要求用户必须常驻打开"文件传输助手"。会话切走时，合规闸会正确拒绝发送（`wrong_chat_open`，安全无事故），但报告就发不出去。

**目标**：worker 每次自行定位并打开"文件传输助手"会话（或等效的确定性目标通道），然后在正确的会话里发送——用户无需保持任何会话状态。

## 3. 已确认的关键事实（不要重走弯路）

1. **微信 4.1.13 本机 AX 现状**：只暴露窗口壳（191 节点：菜单栏+标题栏三键）；`session_item_*`/`chat_message_list`/`chat_bubble_item_view` **从未物化**（Swift 原生 AX + pyobjc 双载体交叉验证，90+ 采样）；
2. **已排除的物化手段**：AXEnhancedUserInterface、AXManualAccessibility、VoiceOver 运行、WeChatAppEx 子进程——全部无效；
3. **wechat-mcp 在 4.0.x 上树丰富**：推测 4.1.x 回退了 AX 适配——版本回退验证有条件再做，不阻塞；
4. **Windows 侧方案（wechatauto-replica 的进程内存热激活）踩红线**（写微信进程内存），macOS 不需要走这条路；
5. **搜索定位（Cmd+F/Cmd+V）已废弃**：Cmd+F 打开的是搜一搜网页面板；搜索框坐标点击不稳定；搜索词有落入聊天输入框被误发的实测风险；
6. **裸粘贴+回车的风险**：目标会话不对时会把内容发进错误会话（今天的 P0 教训，合规闸因此上线）。

## 4. 候选方案（按优先级）

| 方案 | 思路 | 关键风险 |
|---|---|---|
| **A. 侧栏 AX 定位**（推荐首选） | 原生 AX 遍历侧栏 `session_item_文件传输助手` 行 → 合成点击行中心 → 确认 `chat_message_list` 出现 → 粘贴回车 | 本机 4.1.13 内容树未物化——需先解决"树物化"（wechat-mcp 在 4.0.x 可行；4.1.x 是否可物化 = 你要验证的第一个问题，探针 --open2 已备多策略） |
| B. Bundle 级窗口枚举 | CGWindowList/其他非 AX 手段定位会话切换控件 | 未调研到成熟先例 |
| C. 接受现状 + 运维补偿 | 保持"文件传输助手须常驻前台"，解锁后自动补发（已实现） | 用户已否决此终态 |

## 5. 约束（红线，违反即返工）

1. **不碰微信进程内存**（不注入、不 RVA、不 hot-patch——wechatauto 的 Windows 手法在 mac 同样越线）；
2. **不写微信数据库**（本地库只读）；
3. **只发 filehelper**（目标会话白名单硬编码，任何模糊匹配/缺失都不点击）；
4. 发送后 **DB 回读验证**（`#l<id8>` 特征串 + server_id 回执）保留；
5. 审计零正文、零第三方 npm 依赖（探针外部依赖允许，venv 隔离）。

## 6. 验收标准

1. 文件传输助手会话**非前台/非打开**状态下，worker 自动完成：定位 → 打开 → 发送 → 回读命中 → `sent`；
2. 全程零误发（发送前后 DB 对账：除 filehelper 外任何会话零新消息）；
3. 熄屏/锁屏语义保留（deferred，不耗 attempts）；
4. 全量测试绿 + build 干净 + 审计零正文。
