# 说明：报告截止时间窗口问题（回填路径的 `end` 应锚定报告日）

- 版本：v1（2026-10-21）
- 涉及：`src/report.ts`（`generateReport` 回填 / `generateSummary` 回填）、`src/regen-processor.ts`（手动重跑调用方）
- 性质：**语义缺陷说明**（非崩溃、非安全问题）——影响"历史日报告/汇总重新生成"的内容正确性
- 相关裁决：审批/标记的修订语义见 §六（含 2026-10-21 新裁决：正文快照 + 修订流水）

---

## 一、一句话结论

报告与汇总的**统计/取数窗口**必须以"**报告日**"为锚：`[报告日前一日 20:20, 报告日 20:30]`。
当前**回填路径**（手动重跑历史日）把窗口终点写成了"**现在**"，导致跨天统计虚高、报告内容串日、相邻报告重复覆盖。

## 二、问题定义

项目每天的日报窗口规则是（与调度对齐）：

```
日报（报告日 D）窗口 = [D-1 日 20:20, D 日 20:30]
```

- `20:20` 起点 = 10 分钟边界保险（覆盖上一份日报 20:30 截止前的重要消息）；
- `20:30` 终点 = 报告触发时刻。

**正常生成路径**（定时触发）传的是 `asOf = D 日 20:30`，窗口天然正确。
**回填路径**（手动重跑/错号补发）却把 `asOf = 现在`，并把起点改成 `D-1 日 20:20`——

```typescript
// src/report.ts generateSummary 回填分支（现状）
win = { start: dayStart - 86400000 + 20h20m, end: ts /* = 现在 */, dateKey: backfillDateKey }
```

于是当"现在"远晚于报告日时（重跑历史），窗口跨度被拉长到数天。

## 三、后果（以真实数据量级推演）

| # | 后果 | 说明 |
|---|---|---|
| 1 | **统计虚高** | 汇总的 L2「消息 N 条 / @提及 / 关注人物发言」按窗口统计；重跑 06-10 的汇总时窗口变成 `[06-09 20:20, 现在]`，把之后几天的消息全算进去（实测构造：3.7 天跨度）|
| 2 | **排名选择错误** | 汇总按统计排名取前 N 群（`rankGroups`）；虚高的统计会改变"前 N 群"的入选结果 |
| 3 | **内容串日（单群日报）** | `generateReport` 的回填同一问题：重跑 06-10 的日报会把 06-10 20:30 之后（属于次日窗口）的消息也纳入 LLM 归纳——**报告内容包含不属于该日的事实** |
| 4 | **相邻报告重复覆盖** | 20:30 之后的消息按规则属于次日报告；若当日重跑把它们算进来，次日报告再算一次 → 同一消息出现在两份报告里 |

## 四、为什么"到再生成时刻"这个设计不成立

早期理由：错号补发时，正号回归后消息会**异步同步进库**，用 `end=现在`"保证覆盖"。但这个理由不成立：

- 窗口过滤依据是**消息时间戳 `ts`**，不是入库时刻；
- 只要消息 `ts` 落在 `[D-1 20:20, D 20:30]` 内，无论同步发生在什么时候，重跑时都会命中；
- 而 `ts > D 20:30` 的消息**本就属于次日报告**，不应该进 D 的报告。

结论：**回填不需要"现在"，只需要"报告日 20:30"**。

## 五、修法（一行级 + 清理）

| 位置 | 现状 | 改为 |
|---|---|---|
| `regen-processor.ts`（手动重跑） | `generateSummary(now, dateKey)` / `generateReport(..., now, dateKey)` | 传 **`asOf = 报告日 20:30`** |
| `report.ts generateSummary` | 回填分支 `end: ts`（且新增了 `backfillDateKey` 参数） | 删除回填分支——`asOf=报告日20:30` 时，既有 `reportWindow('daily', asOf)` 已算出正确窗口与 dateKey |
| `report.ts generateReport` | 回填窗口 `end = 再生成时刻` | 同上，`end = 报告日 20:30` |

**为什么更干净**：窗口只在 `reportWindow()` 一处定义；回填与正常生成**走同一条代码路径**，不再有特判（与"两种来源分开处理器"的收敛方向一致）。

## 六、修订语义的讨论演进与最终模型（同日拍板）

### 6.1 思想演进（按讨论顺序，含被修正的理解）

**起点（用户最初的需求表述）**：
> "我的想法是那一天的任务就交回给那一天的日报进行修正，但是需要通过简明的方式记录下来改了哪些地方。相当于日报做一个流展示。"

**第一次理解偏差（设计/实现曾采用）**：
> "审批改日报（写修订行）；标记不改日报（只进周/月完成情况段）。"

**第一次修正（用户指出）**：
> "我想说的其实是当天生成报告中增加原有报告的**标记**被改动的部分，不是审批被改动部分——因为实际的变化是标记变化是工作流的移动，审批变化只是确认。"

→ 即：**"修订流"首先承载的是标记（工作流移动）**，而不是审批。

**第二次修正（用户补充）**：
> "审批会导致一些状态的变化，所以这个肯定是有机会改变报告的内容的，但是进别的日的日报的时候是不是就要去分这里的审批和标记了。"

→ 即：**审批同样会改变内容**（`pending_confirm → active/cancelled` 是条目有效性变化），不能简单排除；**关键在于"写进别的日的日报"时，要把审批与标记区分开**。

**第三次修正（用户指出）**：
> "如果没有记错的话审批部分还是可以修改增加条目的？报告这么写就会出现指代不明的问题。"

→ 即：**审批可以修改或增加报告正文中的条目**（确认 → 待确认条目转为有效并补入正文；否认 → 条目移除/标取消）。因此**"正文快照不变、只在修订流水里记"的表述是错的**（自相矛盾、指代不明）。

**第四次修正（用户裁决落位规则，本次最终采用）**：
> "修改了标记的部分需要写入到**当天**（这是工作流的演化）；审批部分的变化则是**落盘当天**即可。"

| 动作 | 写入哪份日报 | 理由 |
|---|---|---|
| **标记**（done/undone/postponed/deleted）| **操作当天**的日报（例：条目 10-14 出身、10-16 标记 → 改 **10-16 日报**）| 标记是**工作流的演化**，属于"今天发生了什么" |
| **审批**（confirm/cancel）| **出身日**的日报（同例 → 改 **10-14 日报**，现状不变）| 审批是对该条目的确认，归属它所在的那份报告 |

修订行的**时间戳**一律 = 操作时刻（"落盘当天"）。级联（周/月）分别跟随各自的日期。

### 6.2 最终模型

**落位规则（审批/标记分别处理）**：

| 动作 | 写入 | 级联 | 修订行时间戳 |
|---|---|---|---|
| 标记 | **操作当天**的日报（工作流演化）| 操作当天所在周/月 | 操作时刻 |
| 审批 | **出身日**的日报（现状不变）| 出身日所在周/月 | 操作时刻 |

示例（条目 10-14 出身、10-16 操作）：标记 → 改 **10-16** 日报；审批 → 改 **10-14** 日报。

**区分点（进别的日的日报时必须分）**：

| 维度 | 审批（confirm/cancel） | 标记（done/undone/postponed/deleted） |
|---|---|---|
| 改变条目什么 | **有效性**（待确认 → 有效/取消） | **工作流状态**（完成/未完成/推迟/删除） |
| 报告正文重渲染 | 条目的存在与确认状态 | 条目的完成状态 |
| 修订行类型与措辞 | 「审批：X 确认为真 / 被否认」 | 「标记：X → 已完成 / 未完成 / 推迟到… / 删除」 |
| 周/月「完成情况」段 | ❌ 不收（那是完成态） | ✅ 收 |

### 6.3 正文修改的准确边界（修正版：审批可修改/补录，正文修订最小化）

**撤回上一版"方案 B（正文快照不变）"的表述**——它与"审批可修改/增加条目"冲突，会造成指代不明。

最终模型：

| 情形 | 正文处理 | 修订流水 |
|---|---|---|
| 审批确认（pending → active）：条目原本**不在**正文 | **补入**对应段落（这就是"修改/增加条目"） | 记「审批：X 确认为真」|
| 审批确认：条目**已在**正文（以"待确认"标注）| 更新该条状态 | 记「审批：X 确认为真」|
| 审批否认（pending → cancelled）| 条目从正文移除或标"取消" | 记「审批：X 被否认」|
| 标记 done/undone/postponed/deleted | 更新/隐去该条 | 记「标记：X → …」|

**"快照"的准确含义**（不是"正文永不改"）：
- **只改受影响段落**，其余正文不动（修订最小化，diff 友好）；
- 每一处改动都在**修订流水**留痕（时间 / 类型 / 来源通道）；
- 正文 + 修订流水共同构成"当时的报告 + 后续的账"。

### 6.4 实现落点（待修）

| 组件 | 现状 | 应改为（最终模型） |
|---|---|---|
| `report-revision.onApproval` | 写修订行 + 重渲染受影响段落 | **保留重渲染**（审批可修改/补录条目）；补入/更新逻辑与"条目当前状态"对齐 |
| `report-revision.markTarget` | 写修订行 + 重渲染 + 级联 | 保留（标记 = 工作流移动）|
| 设计文档 §0/§2 | 审批=改日报、标记=不改 | 按 6.2/6.3 的模型更正（两者都改正文，语义不同）|
