# 说明：报告截止时间窗口问题（回填路径的 `end` 应锚定报告日）

- 版本：v1（2026-10-21）
- 涉及：`src/report.ts`（`generateReport` 回填 / `generateSummary` 回填）、`src/regen-processor.ts`（手动重跑调用方）
- 性质：**语义缺陷说明**（非崩溃、非安全问题）——影响"历史日报告/汇总重新生成"的内容正确性
- 相关裁决：审批/标记的修订语义见 §六（含 2026-10-21 新裁决：正文快照 + 修订流水）

---

## 一、一句话结论

报告与汇总的**统计/取数窗口**必须以"**报告日**"为锚：`[报告日前一日 20:20, 报告日 20:30]`。
当前**回填路径**（手动重跑历史日）把窗口终点写成了"**现在**"，导致跨天统计虚高、报告内容串日、相邻报告重复覆盖。

## 二、问题定义

项目每天的日报窗口规则是（与调度对齐）：

```
日报（报告日 D）窗口 = [D-1 日 20:20, D 日 20:30]
```

- `20:20` 起点 = 10 分钟边界保险（覆盖上一份日报 20:30 截止前的重要消息）；
- `20:30` 终点 = 报告触发时刻。

**正常生成路径**（定时触发）传的是 `asOf = D 日 20:30`，窗口天然正确。
**回填路径**（手动重跑/错号补发）却把 `asOf = 现在`，并把起点改成 `D-1 日 20:20`——

```typescript
// src/report.ts generateSummary 回填分支（现状）
win = { start: dayStart - 86400000 + 20h20m, end: ts /* = 现在 */, dateKey: backfillDateKey }
```

于是当"现在"远晚于报告日时（重跑历史），窗口跨度被拉长到数天。

## 三、后果（以真实数据量级推演）

| # | 后果 | 说明 |
|---|---|---|
| 1 | **统计虚高** | 汇总的 L2「消息 N 条 / @提及 / 关注人物发言」按窗口统计；重跑 06-10 的汇总时窗口变成 `[06-09 20:20, 现在]`，把之后几天的消息全算进去（实测构造：3.7 天跨度）|
| 2 | **排名选择错误** | 汇总按统计排名取前 N 群（`rankGroups`）；虚高的统计会改变"前 N 群"的入选结果 |
| 3 | **内容串日（单群日报）** | `generateReport` 的回填同一问题：重跑 06-10 的日报会把 06-10 20:30 之后（属于次日窗口）的消息也纳入 LLM 归纳——**报告内容包含不属于该日的事实** |
| 4 | **相邻报告重复覆盖** | 20:30 之后的消息按规则属于次日报告；若当日重跑把它们算进来，次日报告再算一次 → 同一消息出现在两份报告里 |

## 四、为什么"到再生成时刻"这个设计不成立

早期理由：错号补发时，正号回归后消息会**异步同步进库**，用 `end=现在`"保证覆盖"。但这个理由不成立：

- 窗口过滤依据是**消息时间戳 `ts`**，不是入库时刻；
- 只要消息 `ts` 落在 `[D-1 20:20, D 20:30]` 内，无论同步发生在什么时候，重跑时都会命中；
- 而 `ts > D 20:30` 的消息**本就属于次日报告**，不应该进 D 的报告。

结论：**回填不需要"现在"，只需要"报告日 20:30"**。

## 五、修法（一行级 + 清理）

| 位置 | 现状 | 改为 |
|---|---|---|
| `regen-processor.ts`（手动重跑） | `generateSummary(now, dateKey)` / `generateReport(..., now, dateKey)` | 传 **`asOf = 报告日 20:30`** |
| `report.ts generateSummary` | 回填分支 `end: ts`（且新增了 `backfillDateKey` 参数） | 删除回填分支——`asOf=报告日20:30` 时，既有 `reportWindow('daily', asOf)` 已算出正确窗口与 dateKey |
| `report.ts generateReport` | 回填窗口 `end = 再生成时刻` | 同上，`end = 报告日 20:30` |

**为什么更干净**：窗口只在 `reportWindow()` 一处定义；回填与正常生成**走同一条代码路径**，不再有特判（与"两种来源分开处理器"的收敛方向一致）。

## 六、修订语义裁决（同日拍板）

**审批与标记都会改变报告内容**，二者都写入"条目**出身日**"的报告，再用**修订流水**记录改动：

| 维度 | 审批（confirm/cancel） | 标记（done/undone/postponed/deleted） |
|---|---|---|
| 改变条目什么 | 有效性（待确认 → 有效/取消） | 工作流状态（完成/未完成/推迟/删除） |
| 修订行措辞 | 「审批：X 确认为真/被否认」 | 「标记：X → 已完成/未完成/推迟到…/删除」 |
| 周/月「完成情况」段 | 不收 | 收 |

**补录边界（2026-10-21 裁决：方案 B）**：审批把 `pending_confirm` 条目变为 `active` 时，若该条目原本不在旧日报正文中——**正文保持快照不变，只在修订流水记录**（「正文快照 + 修订流水」），不把新条目"补进"旧正文。

## 七、测试补充（钉死）

1. 重跑历史日汇总：目标日之后还有消息 → 统计只算目标日（现有用例 fixture 恰好没有后续消息，未覆盖）；
2. 重跑历史日单群日报：目标日之后的消息不进该日报；
3. 相邻两日报告：20:30 之后的消息只出现在次日报告中（不重复）；
4. 审批确认不补录旧正文、只记修订流水；标记照常改动正文与修订流水。

## 八、影响面

- **不影响**：定时生成路径（`asOf = 当日 20:30`，窗口本就正确）、读取层、发送层；
- **影响**：仅"手动重跑历史日"与"错号补发"两条回填路径的内容正确性；
- **数据修复**：无需迁移；如已用错误窗口重跑过历史日，重新重跑一次即可覆盖（同键 upsert）。
